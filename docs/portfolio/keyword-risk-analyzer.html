02 / Product Design목표와 업무 흐름
Design Intent

단순 검출을 넘어
검토의 앞뒤를 연결

해결하려는 업무 마찰

  • 긴 문구에서 등록 표현을 일일이 찾는 반복 작업
  • 띄어쓰기, 줄바꿈, 영문 대소문자, 기호 등 표기 차이
  • 검출 결과만으로는 실제 적용된 매칭 경로를 알기 어려움
  • 아직 원장에 없는 표현이 반복 발견돼도 등록 검토로 연결하기 어려움
  • 이미지 문구는 분석 전에 텍스트로 옮기는 수작업이 발생

제품 목표

  • 검출 위치를 원문에 정확히 대응시키기
  • 검사 방식을 선택 가능하고 다시 설명 가능하게 만들기
  • 분석 결과를 사용자별로 보존하고 공유 통계를 제공
  • 미매칭 표현·문의·등록 승인으로 운영 지식을 갱신
  • 문서 근거 검색은 키워드 매칭과 분리해 보조적으로 제공

사용자 여정

01 · 입력문구 또는 이미지

텍스트 직접 입력 / OCR 추출

02 · 탐지조건 선택과 매칭

모드, 정규화 옵션, 카테고리·등급

03 · 검토근거와 범위 확인

하이라이트, 상세 이유, 원장 정보

04 · 후속수집·문의·관리

후보 큐, 담당자 응답, 승인 등록

관리자와 일반회원

member와 admin은 스크립트 분석, OCR, 미매칭 후보, 키워드 문의, 심의 챗봇, 리포트를 공유합니다. admin에게만 키워드 관리와 사용자 관리가 추가됩니다. 역할은 Supabase Auth의 app_metadata.role을 서버와 화면에서 확인합니다.

설계의 균형
더 많이 탐지하는 것만 목표로 두지 않습니다. 완화된 매칭은 검토 후보를 넓히되 상세 이유를 표시하고, OCR과 AI 추천은 사람이 확인할 수 있는 작업본으로 유지합니다.

03 / System Architecture구성요소와 데이터 흐름
Architecture

공통 분석 엔진과
권한 있는 저장소

React 화면은 FastAPI를 통해 Python 분석 서비스에 요청합니다. FastAPI는 인증·입력 검증·응답 직렬화를 담당하고, 저장소 모듈은 Supabase Auth와 앱 전용 PostgreSQL 테이블을 연결합니다.

사내 사용자 브라우저 │ ├── React / TypeScript (Render Static Site) │ └── Supabase Auth (로그인·세션) │ └── HTTPS JSON API ▼ FastAPI (Render Web Service) ├── service.py → matching_engine.py / approved_matching.py ├── OCR · 키워드 추천 · 규정 검색 보조 모듈 └── repository.py ├── Supabase Auth (역할 확인) └── PostgreSQL / RPC (원장·분석·후보·대화) 선택적 외부 경로: OCR 런타임 / 법령 API / 임베딩·LLM API

프론트엔드

탭형 업무 화면, 공통 상태, 결과 하이라이트, OCR 후보 편집, 역할별 탭 노출.

API·서비스

인증 토큰 검증, Pydantic 요청 검증, 분석·관리·추천·문서 검색 API, 오류 격리.

도메인 엔진

키워드 변형, 표기 정규화, 매칭 구간 및 중복·겹침 정리, 결과 이유 구성.

데이터 계층

키워드 원장, 설정, 분석 기록·히트, 문의·메시지, 후보·문서·대화 저장과 RPC.

저장과 정합성 설계

  • 분석 결과는 요청 ID와 지문을 사용해 재시도 시 중복 집계를 막는 경로를 둡니다.
  • 분석 기록과 고유 키워드 집계는 DB 함수/RPC에서 처리하며 원장 버전 충돌을 확인합니다.
  • 미매칭 수집은 원문 문서나 이미지를 후보 통계와 분리하고, 재시도 ID로 중복 반영을 제한합니다.

배포 설정(render.yaml)이 UI와 API 서비스를 선언합니다. 구성 파일의 존재만으로 현재 배포의 가용성이나 성능을 보증하지 않습니다.

OCR과 사람의 확인

OCR 문장은 자동 확정이 아니라 편집 가능한 후보입니다. 저신뢰 OCR 줄은 공유 미매칭 통계에서 제외하는 정책이 있으며, OCR 화면은 별도 Python 3.13 런타임을 사용합니다.

규정 검색과 AI의 경계

문서 검색은 승인·버전·적용 기준일을 고려하고 인접 문맥을 보존합니다. AI 요약은 설정 시에만 선택적으로 실행되며 출처·원문 대조를 거칩니다. GPT 직접 답변 모드는 검색 인용 경로와 별개입니다.

데이터 준비 상태
저장소의 초기 법령 수집본은 검수 전 참고 자료로 표시되어 있습니다. 사내 승인 문서가 아직 등록되지 않았다면 내부 문서 검색 결과는 비어 있습니다. 문서와 평가 정답이 준비되기 전 검색 품질이나 법률 정확도 수치를 주장하지 않습니다.

06 / Security & Reliability운영 고려사항
Trust Boundaries

권한 경계와 기록 범위를
기능별로 나누다

인증과 권한

Supabase 세션을 확인하고 app_metadata의 admin/member 역할을 사용합니다. 관리자 API는 서버에서 역할을 다시 확인하며, 연동 토큰은 분석·읽기 범위이고 관리자 쓰기 권한을 주지 않습니다.

비밀정보 경계

서버 비밀 키와 외부 AI 키는 서버 환경변수에 둡니다. 브라우저에는 Supabase 공개 키만 사용하며 서버 secret을 Vite 변수에 넣지 않습니다.

분석 데이터

일반 미매칭 통계에는 표현·횟수·시각과 익명 재시도 ID가 저장되며, 계정·원본 문서·이미지는 저장하지 않는 것으로 안내합니다. 분석 기록은 소유자 검사 경로를 둡니다.

외부 AI

규정 근거 검색의 AI 검토는 기본 비활성 상태입니다. 사용 시 필요한 질문과 근거가 API 제공자에게 전달될 수 있으므로 운영 설정과 데이터 취급 정책을 별도로 관리합니다.

품질·복구 설계의 근거

  • 분석 ID와 입력 지문을 이용해 재시도 중복 집계를 억제합니다.
  • 문서 버전·내용 해시·인용 원문을 대화 근거와 함께 보존해 사후 확인을 돕습니다.
  • 요약은 실제 전달한 출처 ID만 인용하도록 제한하고, 원문 발췌 및 인용을 검증합니다.
  • 조건·예외·부정 및 적용 범위를 요약에 남기고, 전체 문서 검토가 아니라는 범위를 표시합니다.
  • AI/법령 검색의 실패는 기본 키워드 분석 결과와 분리된 경로로 처리합니다.
남은 운영 한계
코드와 설정 파일은 실제 서비스의 최신 상태, 가용성, 백업 복구 가능성, 동시 처리 성능 또는 검색의 법적 정확성을 단독으로 입증하지 않습니다. 서버 키가 데이터 API 권한을 우회하는 구조에서는 서버 코드의 역할 검사와 운영 키 보호가 중요한 보안 경계입니다.

현재 저장소와 작업 기록에는 기능 구현과 회귀 검증 기록이 있으나, 검토 시간 절감률·매칭 정확도·사용자 만족도·비용 절감의 운영 측정치는 확인되지 않았습니다. 위 효과는 검증 전의 기대 효과이며 정량 성과로 표기하지 않습니다.
