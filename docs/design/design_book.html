  • 구현: 코드 또는 DB 메타데이터에서 확인한 현재 동작입니다.

  • 예제 데이터는 설명용입니다. 실제 계정, 비밀번호, 서버 키와 연동 토큰을 수록하지 않습니다.

목적과 서비스 범위

등록된 키워드와 리스크 기준을 이용해 입력 문장의 위험 표현을 찾고, 검출 위치와 심의 기준을 보여주는 사내 업무 도구입니다. 관리자는 원장과 분석 설정을 관리하고 사용자는 분석과 공유 통계를 조회합니다. 분석은 규칙 기반 Python 엔진에서 수행하며 외부 생성형 AI를 호출하지 않습니다. 결과는 등록된 원장과 매칭 규칙에 따른 검출 정보이며 자동 심의 승인이나 법적 적합성 판정은 구현 범위에 없습니다.

현재 운영 형태는 Streamlit과 별도 FastAPI가 같은 Supabase 프로젝트를 사용하는 구성입니다. React 화면, 과금, 조직별 독립 저장소, 비동기 대량 작업은 구현하지 않았습니다.

Streamlit은 FastAPI를 HTTP로 호출하지 않습니다. API 프로세스 중단이 곧바로 Streamlit 분석 중단으로 이어지지는 않습니다. 두 프로세스 모두 Supabase와 Python 실행 환경이 필요합니다.

공통화된 범위는 매칭 엔진, 결과 필터와 저장소 모듈입니다. Streamlit의 버튼 처리와 API의 analyze가 완전히 같은 최상위 함수로 통합된 것은 아닙니다. 옵션 기본값과 결과 없는 분석의 저장 방식에도 차이가 있습니다.

분석과 집계 처리

  1. 로그인 정보와 역할을 확인합니다.
  2. 키워드 전체, 컬럼 순서와 revision을 단일 스냅샷으로 읽습니다.
  3. 카테고리와 리스크 필터로 분석 대상 키워드를 먼저 선택합니다.
  4. 매칭 옵션과 공통 설정을 구성하고 원문 위치를 보존하며 완전 또는 일부 일치로 분석합니다. 다른 코드의 겹친 검출은 유지하고 하이라이트에서만 표시 구간을 합칩니다.
  5. API의 record=true 또는 Streamlit의 검출 성공 시 저장 함수를 호출합니다.
  6. 저장 함수는 revision과 요청 중복을 검사하고 분석 기록, 고유 키워드별 이벤트와 누적 조회수를 하나의 트랜잭션에서 갱신합니다.
  7. 화면 또는 JSON 결과를 반환합니다.

정합성과 동시성

관리자 저장과 분석 기록은 kra_state의 단일 행을 잠가 짧은 쓰기 구간을 직렬화합니다. 매칭 연산 자체는 DB 잠금 밖에서 실행합니다. 원장이나 공통 설정이 분석 중 바뀌면 저장 시 revision 충돌을 반환합니다. 원장 편집 시 기존 키워드의 조회수와 마지막 출력일자를 보존합니다.

revision은 원장과 공통 설정 변경 버전입니다. 조회수 증가나 초기화 때 증가하는 데이터 전체 버전은 아닙니다. 분석별 별도 엔진 버전이나 공통 설정 전체 스냅샷은 현재 저장하지 않습니다.

보안 경계

브라우저에는 서버 비밀 키를 전달하지 않습니다. kra_ 테이블은 RLS를 활성화하고 일반 클라이언트 역할의 직접 권한을 회수했습니다. 서버 키는 RLS를 우회하므로 앱의 역할 검사와 분석 소유자 검사가 실제 사용자 접근 경계입니다. 키를 가진 서버 코드를 신뢰하는 구조이며 사용자별 RLS가 적용된 브라우저 직접 접근 구조가 아닙니다.

원문 전체를 DB에 저장하지 않지만 입력 지문, 검출 단어와 기준은 저장됩니다. 원문과 세션 토큰은 앱 메모리에 존재할 수 있습니다. 로컬 .env와 Streamlit Secrets는 배포 산출물과 문서에 포함하지 않습니다.

인터페이스 원칙

FastAPI가 제공하는 HTTP JSON API입니다. 로컬 기본 주소는 http://127.0.0.1:8000이며 운영 도메인은 아직 확정하지 않았습니다. 업무 경로는 /api/v1 아래에 있고 상태 확인 경로는 루트에 있습니다. 요청과 응답은 UTF 8 JSON으로 처리합니다. 공개 운영에서는 HTTPS를 사용합니다.

API를 통한 키워드 등록 편집 삭제와 관리자 초기화 경로는 없습니다. 해당 기능은 Streamlit 관리자 화면을 이용합니다. 현재 상태는 동기 요청 처리이며 작업 접수 후 202를 반환하는 비동기 API가 아닙니다.

API 07 보조 분석

POST /api/v1/auxiliary-analyses는 기존 분석과 별도이며 저장·조회수 증가를 하지 않습니다. 요청은 text(1~20,000자, 공백만 입력 불가), categories, risks, kiwi(boolean, 기본 true), embeddings(boolean, 기본 false), limit(1~20, 기본 10)입니다. 기존 사용자·연동 토큰 인증을 동일하게 적용합니다.

정의하지 않은 요청 필드는 허용하지 않아 422를 반환합니다. 공백만 있는 text를 거절하는 별도 검증은 없습니다. 필터 항목의 문자열 길이나 실제 원장 값 존재 여부도 별도 검증하지 않습니다. Pydantic의 기본 변환 규칙을 사용하며 모든 필드에 strict 모드를 지정한 것은 아닙니다.

신규 연동은 네 개별 옵션을 모두 명시하는 방식을 권장합니다. boolean은 JSON true/false 또는 null만 허용하며 문자열은 422를 반환합니다. 개별 false도 기존 묶음 true보다 우선합니다. 네 필드가 전부 생략/null이면 기존 검출 경로를 유지하며, 일부만 명시한 경우 나머지는 기존 묶음 옵션과 모드에서 유도합니다. 세부 기본값은 분석 로직 설계서의 개별 표기 비교 옵션을 참고합니다.

mode=exact에서 B245 안티에이징(anti-aging)을 안티에이징으로에서도 찾으려면 strip_bracket_notes=true로 지정합니다. 공백과 대소문자 옵션은 별도로 선택합니다. 기호 치환은 공백 치환이므로 피부&보습과 피부보습을 연결하려면 기호·공백 옵션을 모두 켭니다. 조사·어미 허용 목록은 similar 모드에서만 참조하며 exact의 단어 경계를 제한하지 않습니다.

응답 형식과 경로는 유지합니다. 기록 지문은 생략/null인 신규 필드를 제거하고 계산해 기존 기록의 재시도를 보존하며, 명시한 개별 옵션 값은 지문에 포함합니다.

화면과 같은 검사는 mode=exact 또는 partial과 네 개별 옵션을 명시합니다. partial은 등록 표현의 어느 연속된 조각이든 partial_min_len 이상이면 문장 어디서든 찾습니다. 예를 들어 안티에이징 등록 시 에이징 관리가 필요하다는 최소 3글자 O, 4글자 X입니다. 필터는 매칭 전에 적용하고, 개별 옵션 경로에서는 다른 코드의 겹친 결과를 보존하며 같은 코드의 포함된 짧은 조각만 제거합니다. 호환을 위해 mode 생략 시 기존 similar 기본값은 유지합니다.

위치와 하이라이트 규약

start는 0부터 시작하고 end는 마지막 문자 다음 위치입니다. Python에서는 text[start:end]로 구간을 얻습니다. JavaScript의 일반 문자열 인덱스는 UTF 16 단위이므로 이모지가 포함된 원문에서는 Array.from(text).slice(start,end).join('')처럼 code point 기준으로 변환해야 합니다. 표시 구간이 항상 원장 term 문자열과 동일하다고 가정하면 안 됩니다. 정규화와 겹침 병합으로 원문 표시 구간이 넓어질 수 있습니다.

저장과 재시도

record=false이면 DB에 분석 결과와 조회수를 기록하지 않습니다. 이 경우 analysis_id를 받더라도 결과 조회 API에서 찾을 수 없습니다. record=true이면 검출 결과가 없어도 API는 분석 실행 기록을 남깁니다. 저장 전 원장 revision을 검사합니다.

입력 지문은 analysis_id와 record를 제외한 요청 객체를 키 정렬 JSON으로 직렬화한 SHA 256 값입니다. 동일 ID와 호출 주체 및 지문이면 기존 결과를 반환하고 조회수를 다시 올리지 않습니다. 다른 입력이나 다른 주체가 같은 ID를 사용하면 409입니다. 같은 ID를 생략해 재시도하면 새 분석으로 처리되므로 기록 요청에는 클라이언트가 UUID를 생성해 재사용하는 것을 권장합니다.

동일 입력 지문에는 엔진 버전이나 조회된 공통 설정 값 자체가 들어가지 않습니다. 이미 기록된 ID는 설정이 바뀌어도 이전 결과를 반환합니다. 새 설정으로 재분석하려면 새 analysis_id가 필요합니다.

  • 앱 자체의 rate limit, 배치 분석 API, 비동기 큐와 요청별 타임아웃 취소는 없습니다.
  • Supabase HTTP 연결 타임아웃은 5초, 읽기 타임아웃은 30초입니다. 여러 호출을 포함한 전체 API 제한 시간과는 다릅니다.

정확 모드에서 괄호 설명 제외를 끄면 괄호 포함 등록명을 찾는다는 안내를 표시합니다. 예를 들어 등록명 안티에이징(anti-aging)은 안티에이징으로에서 검출되지 않으며, 괄호 옵션만 켜면 괄호 밖 표현도 찾습니다. 공백·대소문자·기호는 별도로 선택합니다. 어떤 옵션도 조사·어미 허용 여부를 전환하는 설정은 아닙니다.

네 옵션은 기본적으로 접힌 키워드 매칭 옵션 익스팬더 안에 배치하며 예시 도움말을 제공합니다. 선택은 모드를 바꿔도 유지되며 옵션이나 검사 방식을 바꾸면 이전 분석 결과를 숨깁니다. 다시 분석 버튼을 눌러야 새 조건으로 실행하고 집계합니다. 기존 세션의 묶음 옵션은 괄호·공백·기호 설정의 초기값으로 옮기며 영문 대소문자 무시는 켜짐으로 유지합니다. 적용 중인 규칙 요약의 모든 문구는 주변 설명과 같은 네이티브 caption 글꼴과 크기를 사용합니다.

키워드 매칭 방식은 세 가지입니다. 완전 일치는 등록 표현 전체가 문장 어디든 포함되면 찾습니다. 일부 일치는 앞·중간·뒷부분의 연속 2글자 이상을 찾습니다. 글자 수 매칭은 같은 원리로 최소 글자수를 조절하며 2이면 일부 일치와 결과가 같습니다. 각 라디오 항목 오른쪽의 물음표에 해당 방식의 설명과 O/X 예시를 제공합니다. 그룹 제목 옆에는 통합 도움말을 표시하지 않습니다. 문장은 마침표 뒤에 빈 줄을 두고 예시)는 별도 문단으로 표시합니다. 안티에이징 등록 시 입력 에이징은 완전 일치 X, 일부 일치 O, 글자 수 매칭 최소 4글자 X입니다.

네 개별 매칭 옵션과 최소 글자수 도움말도 같은 문단·O/X 형식을 사용합니다. 두 고급 역매칭 옵션은 새 일부 일치와 역할이 겹쳐 화면에서 제거하며 API 호환용으로만 유지합니다. 화면 선택값 similar는 일부 일치를 뜻하지만 실행 설정은 mode=partial, partial_min_len=2로 변환합니다. API의 기존 similar 검출 규칙을 사용하는 것이 아닙니다. 요약·설정 안내 문장도 문장별로 문단을 나눕니다.

적용 중인 규칙 요약에는 현재 방식과 네 옵션의 상태, 부분 검색의 실제 최소 글자수를 표시합니다. 현재 세 방식에서는 조사·어미 목록을 사용하지 않습니다. 공통 기호 목록은 기호 처리 옵션이 켜졌을 때 표시합니다. 목록 편집은 관리자 키워드 관리 탭에서 수행합니다. 일부 일치는 등록명의 일부를 찾으므로 괄호 옵션을 꺼도 괄호 밖 일부만 검출될 수 있습니다.

분석 버튼을 누르면 최신 원장을 읽고 클라우드 공통 설정을 다시 읽습니다. 검출된 고유 코드가 있으면 새 UUID로 분석을 기록하고 조회수를 증가시킵니다. 검출이 없으면 안내만 표시하며 Streamlit에서는 분석 실행 행을 저장하지 않습니다. 같은 버튼을 다시 누르면 새로운 분석으로 집계합니다.

UI 11 결과와 하이라이트

별도 보조 분석 익스팬더에서 Kiwi 형태소 분석(기본 켬)과 임베딩 의미 검색(기본 끔)을 선택하고 보조 분석 실행 버튼으로만 호출합니다. 기존 결과 표 열·CSV·조회수·하이라이트는 변경하지 않습니다. 결과는 방식별 후보 목록으로 표시하며 임베딩 실패는 경고로 표시합니다. 원문·필터·보조 옵션을 바꾸면 이전 보조 결과를 숨깁니다. 의미 검색은 위험 확률이 아닌 관련 후보이며 기본 최대 10개를 제안합니다.

검출 성공 시 고유 키워드 수, 원장 정보 표, 위치 표시 선택, 결과 CSV, 원문 하이라이트와 툴팁을 제공합니다. 표에는 kwd_no와 원장 전체 컬럼을 조인해 대체어와 증빙 기준도 보여줄 수 있습니다. 원장의 현재 정보가 조인되므로 과거 결과 전용 불변 스냅샷 뷰는 아닙니다.

표와 CSV는 기존 열 구성을 유지하며 실제 일치 문구 열을 추가하지 않습니다. 입력 에이징 관리에서 일부가 일치하면 등록 키워드 안티에이징을 결과로 표시하며 조각을 새 DB 키워드로 생성하지 않습니다. 원문 일치 범위는 하이라이트와 기존 start/end로 확인합니다.

위치별 분석 결과와 고유 키워드 표시 목록은 분리합니다. 동일 키워드가 두 번 검출되면 위치별 결과에는 두 행이 있지만 화면 발견 건수와 누적 조회 증가 단위는 고유 kwd_no입니다. 서로 겹치는 다른 키워드의 실제 구간은 모두 보존합니다. 같은 키워드의 포함된 짧은 후보만 제거하고 하이라이트에서 겹치는 범위를 합쳐 모든 해당 코드를 표시합니다. 예를 들어 피부와 피부보습이 모두 등록되어 있으면 표에는 두 코드가 남고 원문 구간을 한 번 칠해 두 코드를 함께 표시합니다.

UI 12 원장 목록과 필터

분석 탭 하단에서 키워드 검색, 카테고리, 리스크 등급, 증빙자료유형을 지정합니다. 검색은 키워드명, 대체키워드, kwd_no를 대상으로 하고 필터 적용 버튼으로 반영합니다. 필터 초기화로 조건을 지웁니다. 분석 결과에 적용하는 카테고리 필터와 원장 목록 필터는 별도 상태입니다.

현재 화면은 건수 정렬 후 head를 취하고 선택된 결과를 코드로 다시 정렬합니다. API DB 집계는 건수와 코드를 함께 정렬한 뒤 limit합니다. Top N 경계에서 동점이 많으면 선택되는 코드가 달라질 수 있으며 정렬 통일은 개선 제안입니다.

관리자 키워드 관리 탭 안의 공통 분석 규칙 영역에서 키워드 뒤에 붙는 말 허용 목록과 공백으로 처리할 기호 목록을 관리합니다. 각 폼을 제출해야 저장되며 설정 저장은 관리자만 허용하고 revision을 증가시킵니다. 일반 사용자에게는 이 편집 위젯을 생성하지 않습니다. 드롭다운 편집은 기존 관리자 화면을 유지합니다.

분석하기 탭은 키워드 매칭 방식, 키워드 매칭 옵션과 적용 중인 규칙 요약을 제공합니다. 분석 실행 시 공통 규칙을 다시 읽고 요약도 사용한 스냅샷으로 갱신합니다. 기호는 한 줄에 하나씩 입력하며 쉼표도 저장할 수 있고, 여러 글자를 입력하면 저장하지 않습니다. 빈 기호 목록의 기본값 복원 동작은 유지합니다.

기존 분석 경로에서 자동 수집되지 않던 접미사 후보 안내는 제거했습니다. 후보 제안 기능을 구현하거나 합성어 검출 정책을 변경한 것은 아닙니다.

원장 저장 트랜잭션

  1. 상태 행을 잠그고 전달한 revision과 현재 값을 비교합니다.
  2. rows와 columns가 배열인지, kwd_no가 비어 있거나 중복되지 않는지 검사합니다.
  3. 새 목록에 없는 기존 키워드를 삭제합니다.
  4. 새 키워드를 삽입하고 기존 코드는 data만 갱신합니다.
  5. 컬럼 순서를 저장하고 revision을 1 증가시킵니다.

불일치는 SQLSTATE 40001입니다. 원장 삭제가 기존 이벤트나 실행 기록을 연쇄 삭제하지 않습니다. 기존 코드를 삭제한 뒤 다른 의미의 키워드에 같은 코드를 재사용하면 과거 통계 해석이 섞일 수 있으므로 운영상 재사용을 피해야 합니다.

분석 기록 트랜잭션

상태 행 잠금 후 같은 ID가 있으면 actor와 fingerprint를 확인하고 저장된 결과를 반환합니다. 없으면 revision을 확인하고 kra_runs를 삽입합니다. result.unique_keywords 중 현재 원장에 있는 코드를 골라 이벤트를 넣고 해당 키워드의 hit_count를 1 증가시킵니다. last_hit은 Asia/Seoul 기준 문자열로 기록합니다.

RPC는 서버에서 만든 검출 결과를 신뢰합니다. DB가 원문을 다시 분석하거나 요청자가 계산한 결과의 진위를 검증하는 구조는 아닙니다. 따라서 서버 비밀 키를 가진 외부 클라이언트가 직접 이 RPC를 호출하도록 공개하면 안 됩니다.

초기화와 safeupdate

누적 초기화의 실제 SQL은 다음과 같습니다.

update public.kra_keywords
set hit_count = 0, last_hit = ''
where hit_count <> 0 or last_hit <> '';

Supabase의 safeupdate가 켜진 HTTP 세션에서도 실행되도록 대상 조건을 명시합니다. 안전장치를 비활성화하지 않습니다. 주간 초기화는 이벤트의 visible만 변경하며 기존 분석 ID를 보존해 나중의 중복 요청이 다시 집계되지 않게 합니다.

엔진 경계

matching_engine.py는 Streamlit, Auth와 파일 저장을 사용하지 않는 규칙 기반 엔진입니다. 입력 원문과 pandas DataFrame, 명시적 설정을 받아 Match2 목록을 반환합니다. 조회수 증가와 원장 저장은 엔진 밖에서 수행합니다. NLP라는 함수 이름이 있지만 외부 언어 모델이나 형태소 분석 서버를 호출하지 않습니다.

MatchingConfig는 변경 불가 dataclass입니다. 기본 무시 기호는 /, &, ,, *이며 기본 한국어 조사 어미 목록을 포함합니다. 독립 엔진 호출자는 빈 tuple 또는 frozenset을 전달해 기본 규칙을 비활성화할 수 있습니다. 앱과 API 어댑터는 빈 무시 기호 목록을 기본값으로 되돌리는 기존 동작을 유지합니다.

설정 스냅샷에는 mode(exact/similar/partial), exact_relaxed, partial_min_len, similar_reverse_single, similar_reverse_any, exact_fallback_similar와 exact_fallback_min_tokens도 포함합니다. UI와 API는 이 객체 하나로 엔진을 호출합니다. 기존 match_mode 등 개별 인수는 호환 어댑터인 _resolve_config에서 스냅샷으로 변환하며 명시한 인수가 우선합니다.

화면은 완전 일치, 일부 일치, 글자 수 매칭 - 탐색용 세 가지입니다. 완전 일치는 exact 엔진, 일부 일치는 partial 엔진과 최소 2글자, 글자 수 매칭은 partial 엔진과 사용자 지정 최소 길이를 사용합니다. 따라서 글자 수 매칭을 2로 설정하면 일부 일치와 결과가 같습니다. 기존 similar 엔진과 두 역매칭 옵션은 API 호환 경로에만 남깁니다. 화면의 similar 선택값은 partial+2로 변환하며 API의 similar와 구별합니다. 선택 영역 제목은 키워드 매칭 방식이며 네 개별 옵션은 키워드 매칭 옵션 익스팬더에 배치합니다. 표시 이름은 mode ID와 분리되어 있으며 기존 한국어 모드 문자열을 받는 호환 경로도 유지합니다.

개별 표기 비교 옵션

화면은 네 옵션을 각각 선택하고 명시적인 boolean으로 전달합니다. 새 세션에서는 모두 켜짐입니다. 기존 세션에 묶음 옵션이 있으면 괄호·공백·기호 설정의 초기값으로 한 번 옮기고, 영문 대소문자 무시는 기존 동작대로 켭니다. 선택은 해당 사용자의 세션에만 적용되며 공통 DB 설정을 변경하지 않습니다.

기호 치환과 공백 정규화는 독립 단계입니다. 예를 들어 피부&보습과 피부보습을 연결해 비교하려면 두 옵션을 모두 켜야 합니다. 괄호 제외는 원문의 괄호를 지우는 설정이 아닙니다. 괄호 제거로 생기는 공백도 공백 옵션을 끄면 그대로 비교합니다.

API와 직접 엔진 호출에서 개별 옵션을 모두 생략하거나 null로 주면 기존 알고리즘을 사용합니다. 하나 이상 명시하면 개별 옵션 경로로 처리합니다. 생략한 항목은 기존 묶음 값과 모드에서 유도합니다. 괄호·공백은 exact에서 exact_relaxed, similar/partial에서 true, 대소문자 무시는 true, 기호 처리는 exact_relaxed가 기본입니다. 일관된 결과를 비교하려면 네 값을 모두 명시합니다. 개별 false는 묶음 true보다 우선합니다.

정확 일치 모드

등록 문자열과 허용 후보를 개별 옵션으로 정규화한 뒤 문장 내부의 일치 구간을 찾습니다. 정규화 위치는 원문 위치로 복원합니다. 정확 모드도 원문 전체가 등록 문자열과 완전히 같은지 비교하는 연산은 아니며 단어 내부의 표현도 찾습니다.

strip_bracket_notes를 끄면 비교 표현은 괄호를 포함한 등록명입니다. 켜면 괄호 설명을 제외한 표현으로 준비합니다. 이 준비 단계는 새 완전 일치와 일부 일치가 공유합니다. 괄호 안의 영문만을 독립 별칭으로 추가하는 설정이 아닙니다. 두 방식 모두 조사·어미 허용 목록은 사용하지 않습니다. 완전 일치는 문장이나 단어의 첫머리에서 시작할 필요가 없으며 준비한 표현 전체가 연속해서 포함되면 검출합니다.

예시로 등록 안티에이징은 새로운 안티에이징으로 관리한다에서 O, 에이징 관리가 필요하다에서 X입니다. 등록 피부는 피부과에서도 O입니다. 등록 피부와 피부보습이 동시에 있으면 두 코드를 모두 보존합니다. 같은 키워드가 피부피부처럼 반복되면 앞·뒤 두 위치를 모두 유지합니다.

개별 옵션 없는 호환 호출은 기존 exact_relaxed 값에 따라 기호 연결 비교·유연한 공백·정규화 비교·문자열 검색과 긴 문구 토큰 재시도를 수행하며 긴 키워드 우선 겹침 정책을 유지합니다. 개별 옵션 호출은 이 재시도를 사용하지 않아 꺼진 공백·괄호 조건을 우회하지 않습니다.

기존 유사 키워드 포함 모드 — API 호환용

원문을 영문 숫자 토큰과 한글 토큰으로 나누고 위치를 유지합니다. 키워드 구분자 분리, 괄호 안팎 문자열과 공백 변형을 후보로 사용합니다. 조사 어미 허용 목록, 일부 영어 굴절형과 토큰 단위 비교 및 역매칭 옵션을 적용합니다.

이 모드는 벡터 임베딩이나 의미 유사도 점수를 계산하지 않습니다. 유사라는 이름은 코드에 정의한 표기와 토큰 규칙을 뜻합니다. 단어의 앞부분을 무조건 잘라 후보를 만드는 방식은 제한하며 짧은 변형 후보를 배제하는 규칙이 있습니다.

조사·어미 허용 목록은 이 모드에서만 참조합니다. 으로, 로, 에는은 기본 목록에 포함됩니다. 다만 길이 2 이상인 한글 키워드의 앞뒤에 순수 한글 1~6자가 붙는 경우를 허용하는 합성어 규칙도 별도로 적용하므로, 허용 목록이 모든 검출의 필수 조건은 아닙니다.

개별 옵션 경로에서는 괄호 설명 제외를 끄면 괄호 포함 등록명의 문자열을 요구하고, 켜면 괄호 안팎 후보를 허용합니다. 후보의 토큰 사이 구분자도 선택된 공백·기호 옵션으로 검증합니다. 영문 굴절형·합성어·역매칭에서도 대소문자 선택을 따릅니다. 역매칭과 합성어는 원래 단어 일부를 허용하는 별도 규칙이며 표기 비교 옵션이 이를 단어 전체 검사로 바꾸지는 않습니다. 개별 옵션 없는 기존 유사 모드는 묶음 옵션과 별개로 괄호·공백 변형을 허용하던 동작을 유지합니다.

개별 옵션 없는 기존 호환 호출은 대표 구간을 확장하는 겹침 정책을 유지합니다. 개별 옵션을 명시한 호출은 실제 구간을 키워드별로 보존하며 한 토큰에 여러 직접 일치 위치가 있어도 덮어쓰지 않습니다. 기호 처리를 끄면 토큰 사이뿐 아니라 앞뒤 기호도 비교합니다. 앞 단어만 영문 굴절형인 경우에도 뒤의 일치 단어까지 올바른 범위를 유지합니다. 이 모드는 현재 화면에서 선택하지 않습니다.

일부 일치와 글자 수 매칭 — 공통 부분 문자열 엔진

키워드 내부에서 최소 길이 이상의 연속된 부분 문자열을 만들어 문장 어디서든 찾습니다. 키워드의 첫 글자부터 일치할 필요가 없습니다. 화면 일부 일치의 최소 길이는 2로 고정하고 글자 수 매칭은 2~20, API partial은 2~30입니다. 예를 들어 안티에이징 등록 시 에이징 관리가 필요하다는 일부 일치 O, 글자 수 매칭 최소 3글자 O, 최소 4글자 X입니다. 한 단어·문장 여부에 따른 별도 역매칭 옵션은 사용하지 않습니다.

새 개별 옵션 경로는 완전 일치와 같은 표현 준비·정규화를 거쳐 부분 문자열을 비교하고 원문 위치로 복원합니다. 괄호 설명 제외를 켜면 부분 후보를 만들기 전에 괄호 설명을 제외합니다. 끄더라도 원래 등록명의 일부를 찾는 검사이므로 안티에이징(anti-aging)에서 안티에이징만 검출될 수 있습니다. 대소문자 구분 시 Spot과 spot은 전체가 일치하지 않아도 소문자 pot 조각이 최소 길이를 만족하면 일부 일치가 될 수 있습니다.

중복된 부분 문자열은 한 번만 찾고, 원문 시작 위치마다 가장 긴 끝 위치를 보관합니다. 이어서 같은 키워드의 더 긴 구간 안에 포함된 후보를 제거합니다. 따라서 피부보습 하나가 통째로 일치하면 피부·부보·보습 등 여섯 조각 대신 전체 구간 하나만 남습니다. 다른 키워드 코드와 반복 위치는 제거하지 않으며 ababa에서 aba 두 번처럼 서로 겹치는 별도 출현도 유지합니다. 개별 옵션 없는 API 호출은 기존 부분 후보 반환 정책을 유지합니다.

길이가 L인 문자열의 부분 후보 수는 최소 길이를 고정했을 때 대략 L의 제곱에 비례할 수 있습니다. 이 때문에 전체 처리 시간이 단순 원문 글자수에만 비례한다고 가정하지 않습니다. 긴 문서와 이 모드 조합은 별도 성능 검수가 필요합니다.

정규화와 위치 복원

기호를 공백으로 바꾸는 단계에서는 원문 길이를 보존합니다. 개별 공백 옵션을 켜면 공백·탭·줄바꿈·NBSP·zero width space·BOM을 비교 문자열에서 제외하고 원문 위치 맵을 유지합니다. 끄면 이 문자를 그대로 비교합니다. 영문 대소문자는 선택에 따라 lower를 적용하며 길이가 늘어나는 변환에도 각 출력 글자를 원문 위치로 매핑합니다. 기존 호환 경로의 공백 정규화와 casefold 처리도 별도로 유지합니다.

영문 비교에 lower 또는 casefold를 사용하는 경로가 혼재합니다. Unicode 전체의 모든 대소문자 확장과 문장 부호 조합을 완벽히 처리한다고 검증된 것은 아닙니다. 특수 Unicode 회귀 사례는 추가 검수 항목입니다.

호스팅 배포 설계

render.yaml에는 keyword-risk-ui와 keyword-risk-api Web Service가 정의돼 있습니다. 두 서비스 모두 requirements.lock.txt로 설치하며 $PORT에 바인딩합니다. UI 상태 확인은 /_stcore/health, API는 /healthz입니다. DB 접근까지 확인할 때는 인증된 /readyz를 별도로 호출합니다.

설정에는 starter 플랜이 들어 있습니다. 실제 배포 시 비용과 프로젝트 운영 정책을 확인해야 하며 이 문서에 현재 요금이나 무료 운영 보장을 포함하지 않습니다. 서버 비밀 키는 플랫폼 환경 변수에 입력하고 Git에 넣지 않습니다. Community Cloud에서는 UI에 Secrets 예제를 사용할 수 있지만 별도 API 호스팅은 따로 필요합니다.

공개 API의 도메인, 프록시, rate limit, 접근 로그 보존 기간과 IP 제한은 현재 앱 코드에서 확정하지 않았습니다. 사내 공개 범위와 연동처를 정한 뒤 인프라 설정으로 보완할 항목입니다.

설치와 이관 순서

  1. 신규 프로젝트라면 테이블과 함수가 충돌하지 않는지 확인합니다.
  2. supabase/schema.sql을 한 번 적용합니다. 기존 설치에 반복 실행하지 않습니다.
  3. 초기화 수정 전 설치라면 supabase/fix_reset_counts.sql을 적용합니다.
  4. 서버 환경과 Auth 계정의 app_metadata.role을 지정합니다.
  5. 원본 CSV를 보관하고 import_to_supabase.py로 초기 데이터를 이관합니다.
  6. 행 수, 13개 컬럼, 숫자 조회수와 로그 import_key를 비교합니다.
  7. UI와 API를 시작하고 역할별 접근과 기록 없는 분석을 확인합니다.

4. BGE-M3와 생성 모델 선택

외부 API 전송이 허용됐으므로 초기에는 관리형 임베딩 API + 관리형 생성 API 조합을 우선 평가합니다. BGE-M3는 동일한 광고·법령 자료로 비교할 후보로 유지합니다. BGE-M3를 선택하더라도 처음부터 자체 GPU를 운영하기보다 해당 모델을 제공하는 관리형 엔드포인트와 자체 운영 비용을 비교합니다. 검색 정확도·지연·월 비용이 자체 운영을 정당화할 때 전환합니다. 실제 외부 API 호출은 아직 수행하지 않았습니다.

BGE-M3 공식 모델 카드는 1024차원 임베딩, 최대 8192 토큰, 100개가 넘는 언어와 dense·sparse·multi-vector 검색 지원을 설명합니다. 저자는 하이브리드 검색과 재정렬을 권합니다. 이 특성은 후보 선정 근거이며 한국어 광고 심의에서 가장 우수하다는 보장은 아닙니다. BGE-M3 공식 모델 카드

후속 생성 모델은 특정 Llama-3-Korean 파생 모델로 미리 고정하지 않습니다. 모델별 한국어 근거 준수, 인용 정확도, 상업적 이용 조건, 문맥 길이, 실제 메모리와 응답 시간을 비교합니다. 외부 전송 허용 조건을 임베딩과 생성 단계에 모두 반영합니다. 회사의 범용 외부 전송 허용이 특정 업체의 보관·재학습·처리 지역 조건까지 확인했다는 의미는 아니므로 제공업체 선정 시 해당 조건을 기록합니다. 사용자 비밀번호·서버 키·계정 식별 정보는 모델 입력에 포함하지 않습니다. 서버에서 입력 길이·출력 토큰·사용자별 호출 수·재시도 횟수를 제한하고 API 키는 서버 Secrets에서 관리합니다.

생성 모델에 광고와 문서 내용은 분석 대상 데이터로 전달합니다. 문서 안의 지시를 실행하지 않고 웹 접근·SQL·사용자 관리 도구를 제공하지 않습니다. 출력은 구조화해 파싱하고 인용 ID·원문 위치를 서버에서 확인합니다. 스키마 오류나 인용 불일치가 있으면 검토 결과를 보류하고 확인된 근거만 제공합니다. 허용 사례·부정문·인용문·조건문을 함께 평가하며, 단순히 금지 표현과 의미가 비슷하다는 이유로 모두 위험 처리하지 않습니다. 이미지·배치·음성·전체 상세페이지의 인상은 초기 텍스트 검사 범위에 포함되지 않습니다.

12. 평가와 도입 순서

평가 문항 초안: regulation_eval_cases.jsonl. 실제 법률 검토를 거친 정답이 아니므로 모두 draft이며, 아직 검색 정확도 수치를 산출할 수 없습니다. 원문 적재 후 담당자가 버전별 provision ID에 관련성 정답과 검색 금지 ID를 부여하고 approved로 바꿉니다. 정답은 '위반 여부'가 아닌 '찾아야 할 근거'입니다. 무관 문장도 광범위한 일반 조항과 관련될 수 있어 근거 없음 정답 역시 담당자 검수가 필요합니다.

단계작업완료 기준
1국내 세 제품군·외부 전송 허용 조건 반영, 담당 검수자와 API 제공 방식 선정제품군과 전송 허용은 확정. 문서 승인 책임자·제공업체·모델·예산은 선정 필요
2출처 후보의 원문 확보·청킹·적용일 검수출처·위치·해시·기간 누락 0건, 예외와 표 대조 완료
3세 제품군 각 30개 이상, 총 100개 이상의 관련 조항 라벨 작성일반·변형·부정·조건·제품군 혼동·개정 전후를 포함한 승인 문항
4어휘/관리형 임베딩/BGE-M3/하이브리드 오프라인 비교제품군별 Recall·MRR·지연과 호출·재임베딩 비용 측정
5Supabase 스테이징에 새 구조·검색 RPC 구현날짜·검수·권한 필터 통과, 운영 DB 변경 전 재현 가능한 migration
6FastAPI와 Streamlit에 근거 검색 연결인증·호출 제한·오류 격리·원문 링크와 위치 확인
7사내 파일럿 후 생성 모델 검토실제 누락 유형을 보완한 뒤 인용 검증과 사람 검토 절차 적용

초기 검색 목표 제안: 승인된 관련성 문항 Recall@10 ≥ 0.90, MRR@10 ≥ 0.80, 다른 국가·제품군·기간·미승인 근거의 반환 0건입니다. 담당자가 검수한 최소 100문항의 별도 평가 묶음에서 전체와 각 제품군을 각각 확인합니다. 하나의 제품군이 목표를 넘겨도 다른 제품군의 부족한 품질을 상쇄하지 않습니다. 이 수치는 현재 측정 결과가 아니며, 소수의 예시 문항으로 통과를 주장하지 않습니다. 모델·청킹·질의 확장·임계값 조정에 사용한 문항과 최종 평가 문항을 분리합니다.

추가 의존성 없이 실행하는 평가 도구:

.\.venv\Scripts\python.exe scripts/evaluate_regulation_retrieval.py `
  --cases path/to/approved_cases.jsonl `
  --results path/to/retrieval_results.jsonl `
  --output path/to/metrics.json

정답 JSONL 한 줄에는 case_id, category, judgment_status=approved, relevant_ids, forbidden_ids가 필요합니다. evaluation_type이 scope 또는 generation_safety인 문항은 관련성 집계에서 제외하며 별도 검수합니다. 결과 JSONL 한 줄에는 같은 case_id, 순서대로 정렬한 retrieved_ids, latency_ms, abstained가 필요합니다. ID는 source_key::source_version::provision_key처럼 버전이 포함된 평가용 키를 사용합니다. 근거 없음 정답은 relevant_ids=[], 아직 정답을 모르는 문항은 null로 구분합니다. 도구는 미승인 문항을 정답으로 사용하지 않으며 승인 문항의 결과 누락·중복·알 수 없는 문항 ID가 있으면 실패합니다. 전체와 제품군별 Recall@5/10, MRR@10, 근거 없음 보류 정확도, 금지 근거 반환율@10, 지연 p50/p95를 계산합니다. 이 도구는 모델 실행·임베딩 생성·법률 판단을 수행하지 않습니다. 금지 근거 지표는 라벨에 적힌 ID와 주 근거 상위 10개만 비교합니다. 실제 날짜·국가 필터와 연결된 예외 문맥의 적격성은 DB·API 통합 검증으로 별도 확인해야 합니다.

가장 먼저 할 실제 개발은 공식 원문 확보와 관련 조항 정답 작성입니다. 검색 품질의 기준 없이 LLM·GPU·프레임워크부터 추가하면 모델이 틀린 이유를 구분하기 어렵습니다.
