# 심의챗봇 검색 운영 안내

심의챗봇은 심의자와 관리자가 국가법령정보센터·사내 규정 문서·키워드 DB에서 근거를 찾고 검토하는 React 화면입니다. 검색 결과는 심의자의 검토를 돕는 자료이며 기존 키워드 위험 판정을 변경하지 않습니다.

로그인 권한이 있는 계정으로 사용합니다. 프로그램·계정·서버 키를 처음 준비하는 관리자는 [개발 환경과 계정 준비 절차](development/README.md#도구와-계정)를 먼저 확인합니다.

## 사내 문서 등록과 버전

신규 Supabase 설치에는 `supabase/regulation_corpus_setup.sql`을 적용합니다. 기존 설치에는 `supabase/migrations/20261114013207_regulation_document_auto_metadata_replace.sql`을 적용해야 자동 초안 교체와 같은 날 버전 교체가 동작합니다. 테이블은 RLS와 권한 회수로 브라우저 직접 접근을 막고 FastAPI의 서버 비밀 키만 사용합니다. 관리 API는 Supabase Auth `app_metadata.role=admin`을 다시 확인합니다.

원본 파일 저장에는 [비공개 Storage 적용 절차](regulation-storage-migration.md#기존-환경에-적용할-때)의 Storage 마이그레이션과 서버 설정도 필요합니다. 기존 원본의 이관이 끝난 환경에서는 이관을 다시 실행할 필요가 없습니다.

관리자가 심의챗봇의 **사내 규정 문서 관리**에서 TXT, MD, DOCX, PDF 파일을 초안으로 등록합니다. 한 번에 파일 1개를 등록하며 파일당 최대 50MB, PDF 200페이지 이하, 검색 가능한 본문 20~250,000자, 최대 300개 문단입니다. 앱에서 전체 등록 문서 수를 제한하지는 않지만 문서 목록은 최신 200건까지만 표시합니다. 이미지 전용 PDF는 OCR로 텍스트를 만든 뒤 등록해야 합니다. 원본 파일은 비공개 Supabase Storage에 보관하고 SHA-256을 기록합니다. 브라우저는 원본 바이트에 직접 접근하지 않습니다.

관리자는 상품 카테고리를 직접 입력하고 파일을 선택합니다. 제목은 파일명에서, 새 문서의 식별자는 임의 값으로, 버전은 등록 시각에서 자동 생성합니다. 원본 파일의 SHA-256이 같으면 파일명이 달라도 같은 문서로 인식하고 기존 문서를 기본 선택합니다. 내용이 변경된 경우 서버가 추출 본문으로 기존 승인 문서의 유사 후보를 찾고, 관리자가 교체할 기존 문서 또는 새 문서 등록을 선택합니다. 후보는 참고용이며 유사도만으로 자동 덮어쓰지 않습니다. 내용이 같아도 카테고리 등의 이유로 별도 문서여야 하면 새 문서 등록을 명시적으로 선택할 수 있습니다. 원본 파일·카테고리·적용 기간이 모두 같으면 중복 등록하지 않습니다. 수정본을 기존 문서에 연결하면 이전 초안을 새 초안으로 교체하고, 승인 후 기존 승인본을 이전 버전으로 보관합니다.

시행일과 종료일은 선택 사항입니다. 시행일을 비우면 등록일을 사용하며, 기존 승인본의 시행일이 미래라면 그 날짜를 사용합니다. 종료일을 비우면 기한 없이 검색됩니다. 본문 미리보기와 적용 기간을 검토한 다음 승인합니다. 같은 날 새 버전을 승인해도 검색에는 최신 승인본만 사용합니다. 관리자는 문서 목록에서 초안, 승인본, 이전 버전을 삭제할 수 있습니다. 삭제 시 첨부 원본과 검색 문단도 함께 영구 삭제되며, 삭제한 승인 문서는 검색되지 않습니다. **초안은 검색되지 않습니다.** 검색 기준일에 맞는 승인 이력이 검색됩니다.

새 문서는 문단을 우선 보존하며, 보통 문단은 1,500자를 넘어도 6,000자까지 함께 저장합니다. 바로 뒤의 ‘다만’ 같은 단서 문단도 가능한 한 앞 본문과 묶습니다. 더 긴 문단은 문장 경계를 우선 사용하지만 한 문장이 6,000자를 넘으면 분할됩니다. DOCX 제목과 표의 열 제목·값, PDF 쪽수를 검색 본문에 남깁니다. 복잡한 병합 표의 시각적 관계는 원본 파일에서도 확인해야 합니다. 기존 등록 문서를 자동 재작성하거나 승인본을 교체하지 않습니다.

## 기준일·카테고리별 관련 근거 검색

- 사내 문서는 Kiwi 내용어와 원문 단어로 검색 토큰을 만들고 PostgreSQL 전문 검색을 수행합니다. `pg_trgm` 유사 문자열 검색을 보조로 사용합니다.
- 문서 초안 등록은 OpenAI 호출 없이 저장합니다. 관리자가 **의미 검색 색인 생성** 버튼을 누를 때 `REGULATION_EMBEDDINGS_ENABLED=true`와 `OPENAI_API_KEY`가 설정돼 있으면 `text-embedding-3-small` 임베딩을 생성합니다. 어휘, 유사 문자열, 의미 검색 순위는 RRF로 합칩니다. 임베딩을 만들지 않았거나 기능이 꺼져 있으면 어휘·유사 문자열 검색만 사용합니다.
- 사내 문서의 승인 상태, 상품 카테고리, 기준일을 먼저 적용합니다. 기준일은 사내 문서 버전에 적용되며 국가법령정보센터의 과거 법령 버전을 조회하는 옵션은 아닙니다. 답변 출처에는 문서 ID, 버전, 내용 해시와 문단 ID를 연결합니다.
- 긴 연결 자료는 질문을 반복 포함하는 검색 단위로 나누어 뒤쪽 내용도 검색합니다. 의미 검색이 켜져 있으면 검색 단위들의 임베딩을 묶어 요청합니다. 자료가 길수록 검색 횟수·지연시간과 임베딩 사용량이 늘어날 수 있습니다. 결과 순위를 합쳐 관련 문단 최대 5개를 선택하고, 각 문단의 앞뒤 문단을 같은 문서 버전에서 함께 불러옵니다. 인접 문단 조회가 실패하면 원문 확인 안내를 표시합니다. 이 결과는 관련 문단 검토이며 전체 문서 검토가 아닙니다.
- 국가법령정보센터 범위는 기존 `legislation_source.py`를 사용합니다. 키워드 DB 범위의 **임베딩 기반 의미 유사도 검색**은 현재 등록 키워드 중 문맥상 가까운 후보를 제시합니다. 이 결과를 기존 위험 등급이나 자동 매칭에 합치지 않습니다.

운영 문서와 검토된 질문·정답 문단이 준비되면 `scripts/compare_regulation_search.py`로 원문 PostgreSQL 전문 검색, Kiwi 토큰 전문 검색, 유사 문자열, 의미, 통합 검색을 동일한 사례에서 비교합니다. `scripts/evaluate_regulation_retrieval.py`는 Recall@5/10, MRR, 근거 없음 응답, 금지 출처 혼입과 지연시간을 채점합니다. 평가 사례에는 `case_id`, `judgment_status=approved`, `evaluation_type=relevance`, `question`, `category`, `category_filter`, `as_of`, `relevant_ids`, `forbidden_ids`를 기록합니다. `category`는 평가 분류(`cosmetics`, `food`, `health_functional_food`)이고 `category_filter`는 실제 문서 카테고리 값입니다. 정답 ID는 관리자 본문 미리보기의 문단 ID를 사용합니다. 저장소의 초안 평가 사례만으로 운영 검색 품질 수치를 주장하지 않습니다. 심의자가 확인한 조건·예외의 동반 검색, 주장과 인용의 관계, 버전별 근거 보존도 별도로 평가해야 합니다.

## AI 근거 요약과 사용자별 대화 보존

심의챗봇은 **AI 근거 검토 및 부족한 공식 출처 추가 검색** 옵션을 제공하며 기본값은 꺼져 있습니다. 서버에서 `REGULATION_LLM_ENABLED=true`, `REGULATION_LLM_MODEL`, `OPENAI_API_KEY`를 설정하면 사용자가 옵션을 켰을 때 검색된 근거의 충분성과 충돌을 검토합니다. 중요한 사실이나 값이 빠졌거나 근거가 충돌할 때 OpenAI Responses API의 웹 검색을 사용해 법령, 정부·규제기관 등 공식 도메인에서 추가 근거를 찾습니다. 공식 출처에서 확인할 수 없는 사내 고유 정책이나 값은 추정하지 않고 미확인으로 표시합니다.

별도 **GPT LLM** 검색 모드는 질문과 대화 기록, 사용자가 선택해 연결한 OCR·텍스트 자료를 모델에 직접 전달해 일반 답변을 생성합니다. 이 모드는 법령·사내 문서·키워드 DB 검색과 웹 검색을 실행하지 않으며, 검색 출처를 인용하지 않습니다. 최신 법령·사실 확인이 필요한 답변은 공식 자료에서 별도로 검증해야 합니다. GPT LLM 모드에서 모델 드롭다운을 사용할 수 있으며, 서버의 `REGULATION_LLM_MODEL`은 초기 선택값으로 사용됩니다. 이 값이 없으면 `gpt-6-luna`가 기본 선택됩니다. 실제 응답에는 `REGULATION_LLM_ENABLED=true`와 API 서버의 `OPENAI_API_KEY`가 필요하고, 모델 접근 권한은 OpenAI API 계정에 따라 다를 수 있습니다. 선택한 모델은 GPT LLM 질문에만 적용되며, OpenAI 토큰을 사용합니다. 이는 검색 근거를 검토하는 옵션과 별개의 호출 경로입니다.

AI 답변은 항상 심의 권고이며 위반·적합의 최종 판정이 아닙니다. 내부·검색 근거는 기존 출처 ID로, 웹 검색 근거는 `[WEB1]` 형식으로 답변과 출처 카드에 연결합니다. 웹 검색 인용은 허용된 공식 도메인의 URL만 표시하며, 답변의 각 설명 문단이 실제 검색된 출처 ID를 인용해야 요약을 반환합니다. 이 검증을 통과하지 못하면 생성 답변을 보류하고 추가 확인을 권고합니다. 사내 문서의 검색 문단과 질문은 기존과 같이 외부 AI API에 전송됩니다. AI 요약을 끄면 검색 결과만 표시합니다.

AI 검토에는 사내 문서·키워드 DB·공식 출처가 한 종류에 치우치지 않도록 최대 8개, 본문 합계 48,000자 이내의 근거를 선택합니다. 선택한 근거의 뒷부분을 잘라내지는 않으며, 한도를 넘는 출처는 제외하고 카드에 **검색 결과만 · AI 검토 제외**로 표시합니다. 실제 전달한 출처만 인용할 수 있습니다. 내부·검색 출처를 인용한 설명 문단에는 `「인용 원문」`이 있어야 하며 해당 출처의 실제 원문과 대조합니다. 웹 출처는 공식 도메인의 검색 인용을 확인합니다. 이 검사는 원문 존재와 출처 연결을 확인하는 것으로, 주장이 인용을 올바르게 해석했는지까지 자동 보증하지 않습니다.

요약에는 적용 대상·시행일·조건·예외·부정 표현을 결론과 함께 남기도록 요청합니다. 근거에 없는 조건은 ‘없음’으로 단정하지 않고 미확인 사항으로 다룹니다. 미완성 응답이나 인용 검증 실패 시 요약을 보류하며, 검증 후 답변 뒤쪽을 길이 제한으로 잘라내지 않습니다. GPT LLM 모드에서도 연결 자료를 요약할 때 조건·예외를 보존하도록 요청하지만, 검색·인용 검증을 거친 답변은 아닙니다.

로그인한 사용자의 대화는 사용자 ID별로 저장합니다. 저장된 답변에는 사용된 문서 ID, 버전, 해시와 인용 원문을 붙여 이후 문서가 바뀌어도 당시 근거를 확인할 수 있습니다. 새 대화는 새 스레드를 만듭니다. 관리자도 자신의 대화만 조회하며 다른 사용자의 대화에는 접근할 수 없습니다. 저장된 대화를 선택해 **선택 대화 삭제**를 실행하면 확인 후 그 대화와 메시지·저장 근거가 영구 삭제됩니다. 자동 삭제는 적용하지 않았으며, 드롭다운에는 최근 대화 50개까지 표시합니다.

새로 저장한 대화는 반환된 출처 전체, 인접 문단의 ID·원문, AI 전달 여부를 보존합니다. 예전 대화에서 이미 누락된 근거나 매칭 경로를 복구하거나 추정하지는 않습니다.

## 키워드 매칭 이유와 챗봇 강조의 구분

현재 텍스트 분석의 상세 팝업은 서버가 기록한 실제 매칭 이유, 입력·등록 표현, 사용한 비교 옵션과 주변 문맥을 표시합니다. 내용어 하나가 일치한 결과는 등록 문구 전체의 주장을 뜻하지 않습니다. 이전 결과에 경로 정보가 없으면 미저장 상태를 알립니다. 등록 키워드의 괄호 설명 제외 옵션은 입력 원문의 조건·예외를 삭제하는 기능이 아닙니다.

챗봇의 노란색·파란색 강조는 질문에 포함된 검색어와 표시용 부분 문자열입니다. 질문에 ‘부분 일치’나 ‘유사 표현’을 쓰면 **강조 범위 확대**가 적용될 수 있지만 서버의 검색 조건을 변경하지 않습니다. `「인용 원문」`은 밑줄로 구별합니다. 검색어 강조와 위험 판정, 인용 근거의 검증은 서로 다른 정보입니다. 의미 유사 후보도 기존 위험 등급이나 확정 매칭에 합치지 않습니다.

## AI 키워드 추천 초안

키워드 추천은 등록·등급 변경을 자동 실행하지 않는 검토용 초안입니다.

### 미매칭 키워드 분류 추천

짧은 키워드는 DB에서 해당 표현이 실제로 포함된 사례를 먼저 찾습니다. 예를 들어 `병원`에 대해 `병균`처럼 글자만 비슷한 사례는 추천 근거로 사용하지 않습니다. 여러 상품 카테고리의 사례가 발견되면 등급을 임의로 합치지 않고 카테고리별 DB 사례를 보여 줍니다. 사용자가 상품 카테고리를 선택하면 그 카테고리의 DB 사례와 승인된 사내 규정 문서를 바탕으로 상품카테고리, 리스크 등급, 세부 심의기준 등의 추천 초안을 생성합니다. 모델이 근거를 검증하지 못하거나 호출에 실패하면 선택한 DB 사례값을 초안으로 사용하고 이를 화면에 알립니다.

모델의 카테고리와 리스크 등급은 선택한 상품 카테고리 및 직접 일치한 DB 사례의 값으로 검증합니다. 추천값은 행의 빈 셀에만 채우며 사용자가 입력한 값은 덮어쓰지 않습니다. `병원`처럼 광고 문맥에 따라 해석이 달라지는 표현은 특정 상품군의 DB 사례가 있더라도 단어 자체를 모든 상품군에서 일률적으로 금지한다고 표시하지 않습니다. 최종 등록은 관리자의 기존 검토·승인 경로를 거칩니다. 법령 검색은 서버에 `LEGISLATION_API_KEY`가 설정된 경우에만 추천 근거에 포함됩니다.

운영 React 화면의 OCR 후보와 미매칭 후보 작업본에서 `POST /api/v1/keyword-suggestions`를 호출합니다. 이 API는 기존 키워드 DB의 문자열·선택적 의미 유사 사례, 승인된 사내 규정 문단, 국가법령정보센터 법령·행정규칙 검색 결과를 모아 카테고리·리스크 등급·심의기준·증빙자료유형·대체키워드의 **초안**을 반환합니다. 챗봇의 통합 검색에는 판례 검색도 포함됩니다. 검색 결과와 모델 답변은 최종 심의 판단이 아니며, 추천 API는 키워드 DB를 수정하지 않습니다.

모델 출력은 정해진 JSON 형식으로 받고, 카테고리·리스크 등급이 실제 DB 값인지와 인용한 출처 ID가 검색 결과에 있는지 서버에서 검사합니다. 근거가 없거나 출력 검증에 실패하면 `insufficient`를 반환하고 필드를 채우지 않습니다. OCR 화면에는 행별 추천 근거를 표시하며, 미매칭 후보의 추천값과 근거는 사용자별 작업본에 저장됩니다. 편집한 값은 다시 확인해야 하고, DB 등록은 기존 관리자 승인 경로에서 수행합니다.

API 서비스의 비밀 환경변수로 `OPENAI_API_KEY`와 `REGULATION_LLM_MODEL`을 설정하고 `REGULATION_LLM_ENABLED=true`로 켭니다. `LEGISLATION_API_KEY`를 설정하면 법령·행정규칙 검색 결과도 사용합니다. `REGULATION_EMBEDDINGS_ENABLED=true`를 설정하면 사내 문서와 기존 키워드의 의미 검색을 추가합니다. API 키는 프런트엔드 변수나 저장소에 넣지 않습니다. Render의 기존 서비스에서는 해당 서비스의 Environment 설정에서 값을 등록하고 배포해야 적용됩니다.

도입 전에는 실제 심의자가 확인한 질문·근거와 키워드 등록 사례를 별도 평가 자료로 준비합니다. 근거 검색 적중률, 카테고리·등급 추천 정확도, 근거 없는 추천의 보류율, 관리자 수정률을 추적하고 필요하면 추천 규칙을 조정합니다. 현재 저장된 승인 사례만으로 추천 품질이 검증되었다고 간주하지 않습니다.

## 심의챗봇 서버의 기능 설정과 사용량

`LEGISLATION_API_KEY`는 국가법령정보센터 조회에 필요합니다. `VITE_API_BASE_URL`은 React에서 FastAPI 주소를 가리킵니다. `REGULATION_EMBEDDINGS_ENABLED`와 `REGULATION_LLM_ENABLED`의 기본값은 모두 `false`이므로 AI 근거 검토·추가 검색을 운영에서 사용하려면 API 서비스에 `REGULATION_LLM_ENABLED=true`, `REGULATION_LLM_MODEL`, `OPENAI_API_KEY`를 설정해야 합니다. 비밀 키는 API 서비스에만 둡니다. `REGULATION_MCP_URL`은 사용하지 않습니다.

심의챗봇 아래의 월간 OpenAI 사용량 표시에는 `supabase/migrations/20261112112545_openai_usage_meter.sql`과 `supabase/migrations/20261112112622_openai_usage_service_role_policy.sql`을 적용해야 합니다. 이 집계는 심의챗봇의 LLM 및 사내 문서 임베딩 호출만 포함합니다. 선택 가능한 GPT 모델의 표준 토큰 단가를 사용해 비용을 추정합니다. 현재 서버 기본 모델의 입력·출력·캐시 단가는 `REGULATION_LLM_INPUT_USD_PER_1M`, `REGULATION_LLM_OUTPUT_USD_PER_1M`, `REGULATION_LLM_CACHED_INPUT_USD_PER_1M`으로 재정의할 수 있습니다. 다른 모델의 단가를 조정할 때는 모델 ID의 영문 대문자화 및 구분자 치환값을 사용해 `REGULATION_LLM_MODEL_<MODEL>_INPUT_USD_PER_1M`, `REGULATION_LLM_MODEL_<MODEL>_OUTPUT_USD_PER_1M`, `REGULATION_LLM_MODEL_<MODEL>_CACHED_INPUT_USD_PER_1M`을 설정합니다. 월 예산을 표시하려면 `REGULATION_CHAT_MONTHLY_BUDGET_USD`를 설정합니다. 사내 문서 임베딩은 고정 모델 `text-embedding-3-small`을 사용하며, `OPENAI_EMBEDDING_INPUT_USD_PER_1M`에 가격을 설정합니다.

표시 비용은 응답의 토큰 수와 설정 단가로 계산한 예상치입니다. OpenAI 웹 검색 도구 요금, 장문맥·지역 처리 추가 요금은 합산하지 않습니다. 내장 모델의 표준 단가는 OpenAI 가격 변경에 맞춰 갱신해야 합니다. 지원 목록에 없는 서버 기본 모델은 단가를 설정하지 않으면 토큰 누계만 표시하고 비용 및 잔여 예산은 계산하지 않습니다. OpenAI API 키는 API 서버에만 보관합니다.
